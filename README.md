# auto_git_review

Автоматический ревьюер pull request'ов для локального **Azure DevOps Server**
(on-prem) на базе локальной LLM.

Инструмент снимает рутину первичного ревью: собирает изменения каждого открытого
PR, добавляет контекст истории файлов и просит локальную LLM (через
LiteLLM-шлюз) оценить корректность изменений. Результат — структурированное
резюме с вердиктом и построчными замечаниями, которое публикуется комментарием
прямо в PR.

Всё работает **полностью внутри корпоративного контура** — локальный ALM +
локальная LLM, без внешних сервисов.

## Цель и ожидаемый результат

**Бизнес-задача.** Снять с инженеров рутину первичного ревью pull request'ов в
корпоративном Azure DevOps Server: автоматически находить открытые PR, собирать
изменения и передавать их локальной LLM для оценки корректности.

**Ожидаемый результат использования.** Для каждого открытого PR в целевых
репозиториях формируется структурированное ревью — вердикт
(`approve` / `request_changes` / `comment`), краткое резюме и список построчных
замечаний, — которое публикуется комментарием в PR. Инженер получает готовый
«второй взгляд» на изменения без ручного разбора diff'а.

## Критерии приёмки

Решение считается соответствующим бизнес-задаче, если выполнены все пункты:

1. Инструмент находит все открытые PR в каждом из целевых репозиториев ALM.
2. По каждому PR собираются изменения (diff) и полное содержимое изменённых файлов.
3. Для каждого изменённого файла подтягивается контекст — история последних 5 коммитов.
4. LLM возвращает структурированный JSON-вердикт (`verdict` + `summary` + `comments`).
5. Результат конвертируется в markdown и публикуется комментарием в PR.
6. Повторный запуск не создаёт дублирующих комментариев (dedup по маркеру).
7. Большие PR (превышающие лимит батчей) не падают, а возвращают резюме «требуется ручное ревью».
8. Всё работает внутри корпоративного контура (локальный ALM + локальная LLM).

## Метрики качества

Основная метрика — **точность вердиктов** (доля PR, по которым вердикт модели
`approve` / `request_changes` / `comment` совпал с эталоном эксперта).

| Метрика | Целевое значение |
|---|---|
| Точность вердиктов (accuracy) | ≥ 80% |
| Precision / Recall по классу `request_changes` | ≥ 0.7 |
| Precision / Recall по классу `approve` | ≥ 0.7 |

**Обоснование выбора.** Точность вердиктов напрямую соответствует основной задаче —
автоматизации процесса ревью: верный вердикт и полезные замечания позволяют
инженеру доверять результату без ручной перепроверки.

**Ограничения.** Accuracy может быть смещена при сильной несбалансированности
классов (например, если одобряемые PR значительно превосходят требующие
изменений). Для контроля дополнительно отслеживаются Precision и Recall по
каждому классу; при значительном дисбалансе предусмотрена балансировка
eval-выборки (oversampling/undersampling).

**Порядок измерения.** Метрики вычисляются на eval-датасете (golden set) — наборе
PR с эталонными вердиктами — скриптом прогона (см. `tests/eval/`). Замер
производится при каждом существенном изменении промптов или логики ревью.

## Как это работает

```
                  ┌──────────────────────────┐
                  │   Azure DevOps Server    │
                  │        (on-prem)         │
                  └────────────┬─────────────┘
                               │  REST API (PAT)
                               ▼
   1. Список открытых PR  ──►  2. Diff по каждому PR
   3. Контекст истории файлов (5 последних коммитов)
                               │
                               ▼
                  ┌──────────────────────────┐
                  │     Батчевое ревью LLM   │
                  │      (LiteLLM-шлюз)      │
                  └────────────┬─────────────┘
                               │  JSON-вердикт
                               ▼
   4. Агрегация батчей  ──►  5. Markdown-комментарий в PR
```

### Алгоритм ревью одного PR

1. **Сбор изменений.** Для каждого открытого PR берётся список изменённых файлов
   (`iterations/{id}/changes`).
2. **Контекст файла.** Для каждого файла подтягивается история — 5 последних
   коммитов, затрагивавших этот файл, чтобы модель видела сложившиеся паттерны.
3. **Полный код.** Для изменённых файлов в промпт кладётся и unified diff, и
   **полное новое содержимое** — модель видит весь файл, а не только фрагменты.
4. **Батчевое ревью.** Большие PR режутся на батчи (~8–10k токенов), каждый
   ревьюится отдельным вызовом LLM, результаты агрегируются в один итог.
5. **Dedup.** Перед вызовом LLM проверяется, нет ли уже нашего комментария (по
   маркеру) — повторные запуски не тратят вызовы модели.
6. **Лимит батчей.** Если PR порождает больше `MAX_BATCHES` батчей (например,
   тысячи файлов), полный анализ пропускается и формируется общее резюме
   «нужно ручное ревью».

## Возможности

- ✅ Мульти-проектность и мульти-репозиторность: репозитории в разных проектах ALM
- ✅ Отдельный промпт под каждый тип кодовой базы
- ✅ Батчевое ревью с агрегацией результата
- ✅ Dedup по маркеру — без дублей при повторных запусках
- ✅ Полное содержимое файлов + diff — модель видит весь код
- ✅ Комментарий в PR + markdown-отчёт
- ✅ Полная работа внутри корпоративного контура

## Поддерживаемые типы кодовых баз

| Тип кодовой базы | Промпт |

править без изменения кода.

## Демонстрационный ноутбук

`auto_git_review_research/` — самодостаточная папка для демонстрации проекта
внешней аудитории (комиссия, другие команды) и подачи на валидацию. Центральный
файл — `auto_git_review_research.ipynb`: весь production-код (`config.py`,
`alm.py`, `llm.py`, `prompt.py`, `review.py`, `eval.py`, `monitoring.py`) встроен
в клетки дословно; инварианты H1–H4 (dedup-маркер, лимиты батчей, агрегация
вердиктов, защита `MAX_BATCHES`) проверены на синтетических сценариях, отдельно
показаны мониторинг прогона и оценка качества (разделы 3.3 и 3.5), а в разделе 10
встроены и прогоняются все 41 unit-тест прямо в ноутбуке. Живой раздел ходит в
реальные ALM/LLM только при наличии `.env` и корпоративной сети (комментарии в
PR ноутбук не постит).

Вместе с ноутбуком в папке лежат `README.md`, `ответ_на_замечания_валидации.md`
(+ `.pdf`), `[Номер ЗНО C-1101243] Отчет по валидации.pdf`,
`Автоматический_ИИ_ревью_Pull_Request_v1.pptx`, `.env.example` и
`requirements.txt`. Промпты и unit-тесты в отдельные файлы не выносятся — они
встроены в сам ноутбук (промпты — в словаре `PROMPTS`, 41 тест — в разделе 10),
поэтому папка самодостаточна без `prompts/` и `tests/`.

Все адреса эндпоинтов (ALM, LLM) и имена проектов/репозиториев в ноутбуке и его
`.env.example` — **примеры** (`example.local`, `ExampleProject1`, …); реальные
значения задаются на сервере развёртывания и в демо-материалах не раскрываются.

## Требования

- Python 3.10+
- Apache Airflow (для запуска ДАГа)
- Доступ к Azure DevOps Server (on-prem) с PAT
- Доступ к LiteLLM-шлюзу (OpenAI-совместимый endpoint)

### Установка и запуск

1. Установите зависимости: `pip install -r requirements.txt`.
2. Скопируйте `.env.example` в `.env` и заполните секреты (`AZURE_DEVOPS_PAT`,
   `LLM_API_KEY`).
3. Локальный прогон без Airflow: `python loader/src/run.py` (или используйте
   `loader/src/prepare_env.bat` для подготовки окружения на Windows).
4. Для запуска по расписанию — см. раздел «Запуск в Airflow».

### Тестирование

```bash
pip install -r requirements-dev.txt
pytest
```

Unit-тесты (`tests/`) покрывают чистую логику пайплайна без обращения к ALM/LLM:
агрегацию батчей и dedup, рендеринг промптов, чтение настроек, сборку URL,
разбор ответа LLM, расчёт метрик оценки и агрегацию метрик мониторинга.

### Оценка качества (eval)

Модуль `loader/src/auto_git_review/eval.py` рассчитывает качество ревьюера на
golden-датасете: accuracy, Precision / Recall / F1 по каждому классу вердикта
(`approve` / `request_changes` / `comment`) и confusion matrix. Схема датасета —
`tests/eval/golden_dataset.example.json`. Живой прогон с моделью выполняется в
корпоративном контуре: модель подключается через callable `reviewer(case) -> verdict`.

## Конфигурация

Конфигурация задаётся переменными окружения (см. `.env.example`):

| Переменная | Описание |
|---|---|
| `AZURE_DEVOPS_URL` | База коллекции Azure DevOps Server (без проекта) |
| `AZURE_DEVOPS_PROJECT` | Имя проекта |
| `AZURE_DEVOPS_REPO` | Имя репозитория по умолчанию |
| `AZURE_DEVOPS_PAT` | Personal Access Token (чтение + запись) |
| `AZURE_DEVOPS_API_VERSION` | Версия REST API (по умолчанию `6.1-preview`) |
| `LLM_URL` | Endpoint LLM (`/v1/chat/completions`) |
| `LLM_API_KEY` | Ключ LLM |
| `LLM_MODEL` | Модель (по умолчанию `qwen3:latest`) |
| `POST_COMMENTS` | Публиковать комментарии в PR (`true`/`false`) |
| `VERIFY_SSL` | Проверять TLS-сертификат (`false` для самоподписанных) |

## Запуск в Airflow

1. Создайте Connections:
   - `api_git` — host/port Azure DevOps Server, `password` = PAT;
   - `llm_server` — host/port LiteLLM-шлюза, `password` = LLM API key.
2. Положите ДАГ `dags/prj_brddwh/auto_git_review_dag.py` в `dags_folder`.
3. Положите код проекта в `loader/src/auto_git_review/`.
4. Опишите репозитории в `DAGConfiguration.REPOSITORIES` — укажите для каждого
   `task_id`, `project`, `repo`, `prompt_name` и `post_comment`.

Каждый репозиторий — отдельная таска `PythonOperator`, вызывающая
`review.run_review(repo=..., project=..., prompt_name=..., ...)`.

Основные настройки ДАГа (`DAGConfiguration`):

| Параметр | Описание |
|---|---|
| `REPOSITORIES` | Список репозиториев (тасок) для ревью |
| `MAX_BATCHES` | Максимум батчей на один PR (по умолчанию `20`) |
| `DAG_MAX_ACTIVE_TASKS` | Параллелизм тасок |
| `CONN_ALM` / `CONN_LLM` | Имена Airflow Connections |
| `ALM_COLLECTION_PATH` | Путь коллекции (без проекта) |

## Результат ревью

```json
{
  "verdict": "approve | request_changes | comment",
  "summary": "краткое резюме ревью",
  "comments": [
    {
      "file": "путь/к/файлу",
      "line": 42,
      "severity": "critical | major | minor | nit",
      "text": "текст замечания"
    }
  ]
}
```

Результаты по батчам агрегируются в один итог (вердикт — по приоритету
`request_changes > comment > approve`) и публикуются комментарием в PR, если
включена отправка.
